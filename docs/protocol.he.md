# פרוטוקול SafeRoom — שלב 1

## 1. מבנה המסגרת

TCP הוא זרם של בתים, ולא של הודעות. לכן כל הודעה נשלחת בתוך **מסגרת** (frame).
המסגרת אומרת קודם כול מה האורך שלה, וכך הצד השני יודע כמה בתים לקרוא.

```
+-------------------+-----------+-----------------------------+
| length (4 bytes)  | type (1B) | payload (length - 1 bytes)  |
+-------------------+-----------+-----------------------------+
```

- **length**: מספר ללא סימן, big-endian (פורמט `>I` ב־`struct`). הוא סופר את בית ה־type **וגם** את ה־payload: `length = 1 + len(payload)`.
- **type**: בית אחד (`B`). סוג ההודעה (ראו סעיף 2).
- **payload**: תוכן ההודעה. בשלב 1 זה JSON בקידוד UTF-8.

**כללים בקבלת מסגרת:**
- `length == 0` ← מסגרת לא תקינה, והחיבור נסגר.
- `length > max_frame_size` (ברירת מחדל 1 MiB) ← החיבור נסגר **לפני** שקוראים את ה־payload. זה חוסם לקוח ששולח אורך מזויף וענק (למשל 4GB) כדי לגרום לשרת להקצות זיכרון.

**למה ה־type מחוץ ל־JSON?** בשלב 2 ה־payload יוצפן. המקבל עדיין צריך לדעת את סוג ההודעה בלי לפענח קודם.




## 2. סוגי הודעות

הסוגים מוגדרים ב־`common/protocol.py` בשם `MsgType` (מסוג `IntEnum`).
כל טווח שמור לשלב אחד בפרויקט:

| טווח        | שימוש                          |
|-------------|--------------------------------|
| 0x01–0x0F   | חיבור ותחזוקה (שלב 1)          |
| 0x10–0x1F   | Handshake והצפנה               |
| 0x20–0x2F   | משתמשים: הרשמה, התחברות        |
| 0x30–0x3F   | חדרים                          |
| 0x40–0x4F   | צ'אט                           |
| 0x50–0x5F   | קבצים                          |
| 0x60–0x6F   | סיגנלינג לשיחה (UDP)           |

### הודעות שלב 1

| Type | שם             | כיוון                  | שדות חובה                          |
|------|----------------|------------------------|------------------------------------|
| 0x01 | HELLO          | לקוח ← שרת             | `version` (int), `req_id` (int)    |
| 0x02 | WELCOME        | שרת ← לקוח             | `req_id` (int), `client_id` (str)  |
| 0x03 | PING           | שני הכיוונים           | `req_id` (int)                     |
| 0x04 | PONG           | שני הכיוונים           | `req_id` (int)                     |
| 0x05 | BYE            | שני הכיוונים           | אין (`reason` אופציונלי)           |
| 0x06 | ERROR          | שרת ← לקוח             | `code` (str), `message` (str)      |
| 0x0F | BROADCAST_TEST | לקוח ← שרת ← כל השאר   | `text` (str)                       |

`BROADCAST_TEST` זמני. הוא מוכיח שהשרת יודע לנתב הודעות בין לקוחות, ויימחק כשיהיה צ'אט אמיתי.

**סוגי השדות נבדקים.** `decode_message` דוחה הודעה אם שדה חובה חסר, **או** שהוא מסוג לא נכון. ערך בוליאני לא מתקבל כ־`int` אף פעם (בפייתון, `True` הוא גם `int`).



## 3. דוגמה לכל הודעה

כל הודעה מהלקוח מקבלת `req_id`. הוא מתחיל ב־1 ועולה ב־1.
השרת מעתיק את אותו `req_id` לתשובה שלו, כך שהלקוח יודע לאיזו בקשה התשובה שייכת.

**HELLO** (לקוח ← שרת)
```json
{"version": 1, "req_id": 1}
```

**WELCOME** (שרת ← לקוח)
```json
{"req_id": 1, "client_id": "a3f9c21b"}
```

**PING / PONG**
```json
{"req_id": 2}
```

**BYE** (לקוח ← שרת, או שרת ← לקוח)
```json
{"reason": "server is shutting down"}
```

**ERROR** (שרת ← לקוח)
```json
{"code": "NOT_READY", "message": "send HELLO first", "req_id": 2}
```
`req_id` נכלל רק כשהשגיאה היא תשובה לבקשה מסוימת.

**BROADCAST_TEST**
לקוח ← שרת:
```json
{"text": "hello", "req_id": 3}
```
שרת ← כל לקוח אחר שנמצא ב־READY:
```json
{"from": "a3f9c21b", "text": "hello"}
```

## 4. מצבי הלקוח (בצד השרת)

השרת שומר מצב לכל לקוח מחובר (`ClientState` ב־`server/client_handler.py`).

```
             valid HELLO
CONNECTED  ───────────────►  READY
    │                          │
    │ bad version / timeout    │ BYE / disconnect / server shutdown
    │ bad data / disconnect    │ bad data
    ▼                          ▼
  CLOSED  ◄────────────────────┘
```

| מצב       | משמעות                                    | מה הלקוח יכול לשלוח                 |
|-----------|-------------------------------------------|-------------------------------------|
| CONNECTED | חיבור TCP פתוח, עוד לא נשלח HELLO          | רק `HELLO`. כל דבר אחר ← `ERROR NOT_READY` (החיבור נשאר פתוח) |
| READY     | התקבל HELLO תקין, ונשלח `WELCOME`         | `PING`, `PONG`, `BYE`, `BROADCAST_TEST` |
| CLOSED    | החיבור נגמר                               | כלום. ה־handler מנקה וסוגר את ה־socket |

**כללים:**
- ללקוח יש `hello_timeout` שניות (ברירת מחדל 10) לשלוח `HELLO`. אם לא, הוא מנותק. זה מונע מלקוחות להתחבר, לשתוק, ולתפוס מקום.
- `HELLO` עם `version` לא נכון ← `ERROR BAD_VERSION`, ואחר כך החיבור נסגר.
- `HELLO` שני כשהלקוח כבר ב־READY ← `ERROR BAD_MESSAGE`.
- מידע לא תקין (מסגרת שבורה, JSON שבור, type לא מוכר, שדה חסר או מסוג לא נכון) ← השרת רושם `WARNING`, וסוגר רק את הלקוח הזה.


## 5. קודי שגיאה

קודי השגיאה הם מחרוזות קבועות, שמוגדרות במקום אחד: `ErrorCode` ב־`common/protocol.py`.

| קוד           | מתי השרת שולח אותו                                          | אחרי השגיאה          |
|---------------|-------------------------------------------------------------|----------------------|
| `BAD_VERSION` | `HELLO` עם `version` שונה מ־`PROTOCOL_VERSION` (1)           | החיבור נסגר          |
| `NOT_READY`   | כל הודעה חוץ מ־`HELLO`, לפני שהלקוח ב־READY                  | החיבור נשאר פתוח     |
| `BAD_MESSAGE` | `HELLO` שני, או הודעה שלקוח לא אמור לשלוח (`WELCOME`, `ERROR`) | החיבור נשאר פתוח   |
| `SERVER_FULL` | לקוח חדש מתחבר כשכבר מחוברים `max_clients` לקוחות            | החיבור נסגר          |

**מתי השרת לא שולח שגיאה?**
אם אי אפשר לקרוא את המידע בכלל (מסגרת שבורה, JSON שבור, type לא מוכר, שדה חסר או מסוג לא נכון), השרת לא עונה. הוא רושם `WARNING` וסוגר את החיבור. לקוח ששולח מידע שבור עלול להיות תוקף, ולכן השרת לא משקיע בו עוד עבודה.
